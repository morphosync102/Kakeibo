2026-07-06 のコード調査で洗い出した改善点。優先度順。
着手時は [SPECIFICATION.md](SPECIFICATION.md) と [../AGENTS.md](../AGENTS.md) の不変条件、
GAS 変更を伴う場合は [.agents/skills/kakeibo-gas/SKILL.md](../.agents/skills/kakeibo-gas/SKILL.md) の手順に従うこと。

## P1 — 明細編集操作の統一(ユーザー報告: 画面によって編集・削除ができない)

現状の対応表は [CODEMAP.md](CODEMAP.md) を参照。ゴールは
「**明細が見えるすべての画面で、タップ → 同じ詳細モーダル → 日付・カテゴリ・金額の変更と削除ができる**」こと。

### 1-1. GAS に `updateTransaction` action を新設(金額変更を可能にする) ✅ 対応済み (2026-07-07)

- 症状: 金額(および店舗名)を変更する手段がどの画面にもない。
- 原因: GAS 側に単一明細の汎用更新 action が存在しない(`gas/コード.js` の doPost 分岐参照)。
- 方針: `updateTransactionDate` と同じ厳密照合方式(MessageId + 変更前日付 + 店舗名 + 変更前金額)で
  1件を特定し、金額・(任意で)店舗名・カテゴリを更新する action を追加。
  成功後 `clearCache(source)`。呼び出し側・`test/gas-*.test.mjs`・SPECIFICATION の API 契約表を同時更新。
- GASデプロイ: **必要**(GAS 先行 → Vercel の順)。

### 1-2. ExpenseDetailModal に金額編集 UI を追加 ✅ 対応済み (2026-07-07)

- 対象: `components/ExpenseDetailModal.tsx`(日付エディタと同じ構成で金額欄 + 保存ボタン)。
- 依存: 1-1 が本番デプロイ済みであること。

### 1-3. カレンダーの日別明細から詳細モーダルを開く ✅ 対応済み (2026-07-07)

- 症状: カレンダー(`components/CalendarView.tsx` の日別明細)は削除しかできない。
- 方針: 明細タップで `ExpenseDetailModal` を開く(Dashboard と同じ `selectedExpense` パターンを再利用)。
  インラインの削除ボタンはモーダル内の削除に置き換え。
- GASデプロイ: 不要(1-2 と同時なら 1-1 に依存)。

### 1-4. 「この1件だけ」のカテゴリ変更オプション ✅ 対応済み (2026-07-07)

- 症状: カテゴリ変更は常に「同一店舗の全明細(両source)+ Config の自動分類ルール」一括で、
  1件だけ変えたいケース(同じ店で用途が違う買い物など)に対応できない。
- 方針: モーダルで「この明細のみ / この店舗すべて」を選択式にする。
  「この明細のみ」は 1-1 の `updateTransaction`(category のみ更新)を利用。
- GASデプロイ: 1-1 に含まれる。

### 1-5. `deleteTransaction` を厳密照合へ移行(既知制約の解消) ✅ 対応済み (2026-07-07, id のみは旧クライアント互換で先頭一致)

- 症状: MessageId の先頭一致で1件削除するため、同一メール由来の複数明細がある場合に
  意図しない行を消す可能性がある(AGENTS.md / SPECIFICATION.md 記載の既知制約)。
- 方針: `updateTransactionDate` と同じ照合(id + date + merchant + amount)へ移行。
  呼び出し側(`ExpenseDetailModal.tsx`、`CalendarView.tsx`)と GAS を**同時に**変更する。
- GASデプロイ: **必要**。

## P1 — 体感速度(ユーザー報告: レスポンスが遅い)

根本原因は GAS Web App のレイテンシ(コールド時 1〜3 秒)+ 書き込み後キャッシュ無効化による
コールドリード。GAS を残す前提では「GAS を待たせない UI」にするのが効果的。

### 2-1. 固定費一覧のキャッシュバスター除去 ✅ 対応済み (2026-07-07)

- 症状: 管理画面の固定費タブを開くたびに数秒待つ。
- 原因: `components/ManageView.tsx` の `fetchFixedCosts` が `t=${Date.now()}` を付けるため
  Next.js の fetch キャッシュ(URLキー)が毎回ミスし、常に GAS 直行になる。
- 方針: `t` パラメータを除去し、`app/api/expenses/route.ts` で固定費 GET に `fixedCosts` タグを付与。
  `addFixedCost` / `deleteFixedCost` の POST 成功後に `revalidateTag('fixedCosts')`。
- GASデプロイ: 不要。**最も低リスクで効果が分かりやすい**。

### 2-2. 書き込み操作の楽観的更新 ✅ 対応済み (2026-07-07)

- 症状: 削除・日付変更・追加のたびに全明細を GAS から再取得し、完了まで待たされる。
- 原因: 各ハンドラが成功後に `refresh()`(全件再取得)を呼ぶだけで、ローカル state を即時更新しない。
- 方針: `hooks/useExpenses.ts` に楽観的更新用のミューテーション関数
  (例: `removeLocal(expense)` / `updateLocal(expense)`)を追加し、
  UI は即時反映 → バックグラウンドで再取得・失敗時ロールバック。
- GASデプロイ: 不要。

### 2-3. `alert()` / `confirm()` を非ブロッキング UI へ置換 ✅ 対応済み (2026-07-07, sonner)

- 症状: 操作のたびにブラウザダイアログで全体がブロックされ、遅く感じる。
- 対象: `ExpenseDetailModal.tsx`、`CalendarView.tsx`、`ManageView.tsx`。
- 方針: トースト(成功/失敗)+ 破壊的操作は Undo 付きトーストまたはモーダル内確認に置換。
- GASデプロイ: 不要。

### 2-4. POST レスポンスで更新後データを返す ⏸️ 見送り (2026-07-07)

- 方針: GAS の書き込み action が更新後の明細一覧(または差分)を返せば、
  書き込み後の再取得(コールドリード)を丸ごと省略できる。2-2 で体感が十分なら不要。
- GASデプロイ: **必要**。
- **見送り理由**: 2-2 の楽観的更新により、この案が解決するはずだった「書き込み後の待ち時間」は
  体感上ゼロになった(再取得はユーザーが気づかない裏で走る)。一方で実装には GAS の全書き込み
  action・Next.js プロキシ・クライアントの3層でレスポンス契約の変更が必要で、返却データと
  キャッシュの不整合リスクも伴う。知覚できない裏処理の削減に見合わないと判断。
  バックグラウンド再取得が別の理由(GAS 実行クォータ、通信量など)で問題化したら再検討する。

## 2026-11-07 追加調査

GAS・API層と画面層を分けてコード調査した結果。優先度は「データ消失・誤操作・セキュリティ > 体感速度 > UX > 品質」。
各項目は実コードで確認済み(5-1 の Next.js 挙動のみ実機確認が必要)。

### P0 — セキュリティ・データ整合性

#### 4-1. GAS Web App に認証がない ✅ 対応済み (2026-11-07、移行期間の素通し削除は未対応)
- 対象: `gas/コード.js` の `doGet` / `doPost`、`app/api/expenses/route.ts`。
- 症状: GAS の URL を知っていれば、Vercel のログインを経由せず全明細の取得・削除・カテゴリ一括変更ができる。
- 方針: Script Properties に共有シークレットを置き、プロキシが本文/クエリで送り、GAS 入口で照合する。
  移行は「未設定なら素通し」でGASデプロイ → Vercel に設定 → 照合必須化。
- 対応 (2026-11-07): GAS は Script Property `PROXY_SECRET` が設定されていれば doGet(クエリ `key`)/doPost(本文 `key`)を
  SHA-256 ダイジェストの定数時間比較で照合し、不一致・欠落は `{error:'Unauthorized'}`(LINE webhook は対象外、読み書き不可)。
  プロキシは `GAS_PROXY_SECRET` があれば `key` を付与し、クライアントの `key` は除去、キャッシュキー・ログ・応答に含めない。
  手順は SPECIFICATION「プロキシ認証(GAS)」。
- **未対応(後続タスク)**: 移行完了後、GAS の「`PROXY_SECRET` 未設定なら通す」処理を削除し未設定時は拒否にする
  (あわせてプロキシも `GAS_PROXY_SECRET` 未設定時はエラーにするか検討)。
  将来的には一覧取得も doPost のアクションにして、秘密値を URL(GET クエリ)から完全に外す。
- GASデプロイ: **必要**(Vercel 環境変数も)。

#### 4-2. 明細一覧のキャッシュが 100KB 上限で失敗すると doGet 全体が落ちる(潜在) ✅ 対応済み (2026-11-07)
- 対応 (2026-11-07): `putAll` でチャンク分割保存(`<key>_<gen>_chunks` + `<key>_<gen>_N`)、欠けたらミス扱い、保存失敗は try/catch でログのみ。sourceごとの世代トークン(`kakeibo_<src>_gen`)を `clearCache` で更新し、doGet は読み込み前に取得した世代が保存直前も同じときだけ保存する(書き込み前に読み始めた古い一覧が残るレースと、異なる世代のチャンク混在を防止)。`clearCache` は世代更新前に `SpreadsheetApp.flush()` し、例外を投げない(書き込み成功後の無効化失敗はログ+現世代チャンク削除で代替し、書き込みは success を返す)。プロキシ側: GET を `unstable_cache` 経由にし、配列以外は例外→502でキャッシュしない(2026-11-07)。
- 対象: `gas/コード.js` の `getExpensesWithCache` / `getFixedCostsWithCache` の `cache.put`。
- 症状: 行数がおよそ 700〜900 を超えると毎回の一覧取得がエラーになる。`{error}` 応答は Next.js 側で1時間キャッシュされ得る。
- 方針: `cache.put` を try/catch、またはチャンク分割(`putAll`)。プロキシは配列以外をキャッシュしない。
- GASデプロイ: **必要**。

#### 4-3. 削除したカード明細がメール取込で復活する
- 対象: `extract*Emails`(`newer_than:5d` + Data シートの MessageId 有無で重複判定)。
- 方針: 処理済み MessageId を明細とは別に記録(Gmail ラベル or Processed シート)。
- GASデプロイ: **必要**。

#### 4-4. `deleteFixedCost` が行番号指定 ✅ 対応済み (2026-11-07)
- 対応 (2026-11-07, GAS側): type/name/amount/day(+任意 category)で照合削除(id の行が一致しなければ全行検索、なければ `Fixed cost not found`)。照合フィールドが無い旧呼び出しは id を検証(0以上の整数・範囲内)して従来どおり行番号削除、ヘッダ行は削除不可。UI(`ManageView` の `handleDelete`)も id と type/name/amount/day/category を送るよう対応済み(2026-11-07)。
- 症状: 連続削除や手編集後の古い一覧から削除すると別の固定費を消す。id=-1 でヘッダ行削除。UI は失敗でも成功トースト。
- 方針: 名前・金額・日・種別で照合して削除、id 検証、UI で `data.success` 判定。
- GASデプロイ: **必要**。

#### 4-5. 書き込みに LockService がない ✅ 対応済み (2026-11-07)
- 対応 (2026-11-07): doPost の全書き込み action、`processFixedCostsForSource`、メール取込の重複判定+追加を `runWithScriptLock`(`tryLock(20000)`、try/finally で flush → release)で囲む。取得できなければ doPost は `{error:'Busy'}`、メール取込はログを残してスキップ(次回トリガーが `newer_than:5d` で再取込)。固定費トリガーは `tryLock(120000)` で長めに待ち、取れなければ当日分は翌日以降も補完されない旨を警告ログに出す(6-1 の取りこぼし対策は別途)。
- 症状: 「全件読む → i+1 行目に書く」の間に別の削除が入ると隣の行を書き換える。取込の多重実行で二重登録。
- 方針: 書き込み処理全体を `LockService.getScriptLock()` で囲み、ロック内で再読込・照合。
- GASデプロイ: **必要**。

#### 4-6. source を検証していない ✅ 対応済み (2026-11-07)
- 対応 (2026-11-07, GAS側): `normalizeSource` で省略/空文字/`main`/`yahoo` のみ受理し、他は `{error:'Invalid source'}`(doGet/doPost 共通、LINE webhook 判定はその前)。キャッシュキーも正規化。プロキシ側も GET/POST で省略/`main`/`yahoo` 以外を GAS を呼ばず 400 で拒否(2026-11-07)。
- 症状: `'yahoo'` 以外は全て main 扱い。`'Yahoo'` 等のバグで個人用明細が家庭用シートへ混入し得る。未知 source のキャッシュキーは clearCache されない。
- 方針: プロキシと GAS で `main` / `yahoo` 以外を 400 で拒否、キャッシュキー正規化。
- GASデプロイ: GAS 側は必要(プロキシ側のみなら不要)。

### P1 — 体感速度(最優先)

#### 5-1. 書き込み後の `revalidateTag(tag, 'max')` で直後の再取得が古いデータを返す ✅ 対応済み (2026-11-07)
- 対象: `app/api/expenses/route.ts`。Next 16 の `'max'` は stale-while-revalidate。
- 症状: 保存直後の再取得で編集前の値が返り、楽観的更新が巻き戻る/削除した明細が復活する。
- 方針: `revalidateTag(tag, { expire: 0 })` で即時失効。
- GASデプロイ: 不要。

#### 5-2. 日付・金額の変更が GAS の応答待ち ✅ 対応済み (2026-11-07)
- 対象: `components/ExpenseDetailModal.tsx` の `handleUpdateDate` / `handleUpdateAmount`。
- 症状: カテゴリ変更・削除は即時反映なのに、日付・金額は GAS 往復(数秒)まで閉じない。
- 方針: 他操作と同じ楽観的更新(即反映して閉じる → 裏で送信、失敗時はトースト + 再取得で復元)。
- GASデプロイ: 不要。

#### 5-3. 裏の取得結果が後から行った編集を上書きする ✅ 対応済み (2026-11-07)
- 対象: `hooks/useExpenses.ts`。
- 症状: 起動直後の裏取得が終わる前に編集すると、届いた古い結果で巻き戻る。削除成功時は再取得しないため復活したまま残る。
- 方針: ローカル変更の世代カウンタを持ち、変更より前に始まった取得結果は破棄する。
- GASデプロイ: 不要。

#### 5-4. 手動入力・固定費操作が GAS の応答待ち ✅ 対応済み (2026-11-07)
- 対象: `components/ManageView.tsx`。
- 方針: 送信直後に入力欄をクリアして成功扱いにし、失敗時のみエラートースト(入力内容を復元)。
- GASデプロイ: 不要。

#### 5-6. 楽観的更新の書き込みが並行送信され、連続編集が照合に失敗する ✅ 対応済み (2026-11-07)
- 対象: `lib/write-queue.ts`(新規)、`components/ExpenseDetailModal.tsx`、`components/ManageView.tsx`、`hooks/useExpenses.ts`。
- 症状: 同じ明細を「金額変更→すぐ日付変更/削除」すると、2回目の厳密照合(変更後の値)が
  サーバー未反映のため `Transaction not found`。書き込みAの再取得がBの完了前に返るとBが一時的に巻き戻る。
  手入力の失敗時復元が、その後に入力中だった別内容を上書きする。
- 方針: 全 POST を1本の Promise チェーン(`postWrite`、`keepalive: true`)で順番に送る(前の成否に関わらず次を送る)。
  `useExpenses` は未完了の書き込みがある間、または取得開始後にローカル変更があった取得結果を適用せず
  (`shouldApplyFetch`)、キューが空になった時点で再取得して収束させる。
  手入力の失敗時は入力欄(店名・金額)が空でマウント中のときだけ復元し、それ以外は失敗内容をトースト表示。
- 追補 (2026-11-07): 書き込み中に始まった取得Yが、完了後に始まった取得Zより後に返ると古い値で上書きする問題に対し、
  キューの完了数(`settled`)を取得の前後で比較し、取得開始時に未完了の書き込みがあった/取得中に完了した結果も破棄
  (`fetchDiscardAction` で、より新しい取得が無ければ取り直す)。`postWrite` に `AbortSignal.timeout(45秒)` を付け、
  時間切れは失敗として次の書き込みへ進む(`keepalive` と併用可)。
- 追補2 (2026-11-07): タイムアウトは `WriteTimeoutError`(`isWriteTimeout`)として通常の失敗と区別し、手入力では入力欄を
  復元せず、モーダル・固定費でも「反映されている可能性があります。一覧で確認してください」と表示する(再送による二重登録防止)。
  書き込み前に読み始めた GET が `revalidateTag` 後に `unstable_cache` へ古い一覧を保存するレースに対し、書き込み後・破棄後・
  手動の再取得は `fresh=1` で Next.js キャッシュを迂回し、キャッシュは5分に短縮。API ルートに `maxDuration = 60`。
- GASデプロイ: 不要。

#### 5-5. メール取込・固定費トリガーの追加分が最大1時間画面に出ない
- 症状: トリガーは GAS キャッシュのみ消し、Next.js の `expenses` タグ(1h)は残る。
- 方針: Next.js 側の revalidate を短縮(例: 5分)、またはシークレット付き再検証エンドポイントをトリガーから呼ぶ。
- 部分対応 (2026-11-07): Next.js の一覧キャッシュ(`unstable_cache`)を 5分に短縮し、手動の再取得は `fresh=1` で
  キャッシュを迂回して GAS を直接読むようにした(遅延は最大5分、再取得ボタンで即反映)。再検証エンドポイント案は未対応。
- GASデプロイ: 再検証エンドポイント案なら必要。

### P2 — 正確さ・UX

- 6-1. 固定費が 29〜31 日指定だとその日がない月に登録されない。トリガー失敗日も取りこぼす
  (`min(day, 月末) <= today` + 既存 uniqueId で重複防止)。GASデプロイ必要。
- 6-2. 取得データを正規化していない。手編集の `"1,200"` や空日付で合計が文字列連結・`undefined月`・

- 6-3. 詳細モーダルの配色が画面テーマではなく OS のダークモードに従う(`isDarkMode` を渡す)。
- 6-4. モーダルで1項目保存すると他項目の未保存変更が黙って消える(保存ボタン統合 or 警告)。
- 6-5. ダッシュボードのカテゴリ絞り込みに収入が混ざる(「その他」が両方に存在)。
- 6-6. iPhone のセーフエリア: `viewportFit: 'cover'` なし、`safe-area-top` / `scrollbar-hide` が未定義、
  Dashboard/Manage の下余白不足で最終行や保存ボタンが下部ナビに隠れる。
- 6-7. 管理画面: 固定費追加・削除がサーバー失敗を判定しない、`alert()` が1か所残存、手動入力の金額未検証。 ✅ 対応済み (2026-11-07)(4-4 の GAS 側照合は未対応)
- 6-8. 店舗一括カテゴリ変更で画面上は1行しか変わらない。未変更でも保存できる。
- 6-9. カレンダーで斜めの縦スクロールでも月が切り替わる(`|dx| > |dy|` 判定)。
- 6-10. カテゴリ学習が先勝ちの部分一致で、後から追加した具体的なルールが効かない(最長一致優先)。GASデプロイ必要。

### 推奨する方向性(段階的)

1. **UI を全操作「即時反映」に統一**(5-1〜5-4)。バックエンドがどれだけ遅くてもタップの体感はほぼゼロになる。最小コストで最大効果。
2. **明細に一意ID列を追加**(例: `Id` 列に UUID、取込・手動入力時に採番、既存行はマイグレーションで採番)。
   更新・削除は ID 指定に統一し、照合ロジックと行ずれ問題をまとめて解消する。GAS API 契約変更を伴う。
3. **デプロイを1本化**: GitHub Actions で「GAS デプロイ → 成功したら Vercel デプロイ」を順に実行し、push だけで両方を正しい順序で反映する。
4. **ホスティングと認証**(下記の比較で選択)。

### ホスティング比較(公開URLの不安 vs 速度)

速度を決めているのは「どこでホストするか」より「データが GAS/Sheets にあること」。
Vercel から NAS へ移しても GAS を経由する限り体感はほぼ変わらない(関数が米国リージョンなら NAS の方がむしろ近い)。

| 案 | 公開範囲 | 速度 | 手間・リスク |
| --- | --- | --- | --- |
| A. Vercel のまま硬化 | URL は公開、パスワード + 試行制限 + GAS 認証 | 現状維持 | 小。4-1・7-1 を直せば実用上十分 |
| B. Vercel + Cloudflare Access 等の前段認証 | 許可したメールアドレスのみ | 現状維持 | 中。独自ドメインが必要 |
| C. NAS + Tailscale(Next.js を NAS で動かし GAS はそのまま) | tailnet 内の端末のみ(外から見えない) | ほぼ同等 | 中。家族の端末にも Tailscale が必要。NAS 停止時は使えない |
| D. NAS + Tailscale + データをローカル DB(SQLite)へ | 同上 | **最速**(数十ms)。GAS 待ちが消える | 大。GAS は Gmail 取込・LINE 通知の役だけ残し、NAS の API へ書き込む形に作り替え。Sheets は閲覧用エクスポート |
